# humanoid_mpc_config

The typed schemas of the MPC hyperparameter files. Every file that tunes the MPC, the robot's controller or the tuning
GUI is a textproto of one message of this package, parsed strictly (an unknown key, a value of the wrong type or a key
given twice is an error with its file, line and column) into a plain C++ struct (`ocs2::humanoid::mpc_config::<Name>`,
generated by nproto, tools/nproto/README.md) or a Python message:

| File | Message | Read by |
|---|---|---|
| `robot_models/<robot>/<package>/config/mpc/task.textproto` | `TaskFile` (`task_file.proto`) | the MPC, the robot process, the visualization, the GUI |
| `.../config/command/reference.textproto` | `ReferenceFile` | the target trajectories, the teleoperation, the validation driver |
| `.../config/controller/joint_pd_gains.textproto` | `JointPdGainsFile` | the MRT joint controllers, the GUI's PD gains tab |
| `.../config/mpc/contact_planning.textproto` | `ContactPlanningFile` | the contact planner (Atlas, SA01) |
| `humanoid_nmpc/humanoid_common_mpc/config/command/gait.textproto` | `GaitFile` | the procedural motion manager |
| the bus topic `operator/mpc_parameters` | `MpcParameterUpdate` | the MPC's parameter updater, the robot's controller-side settings |
| the bus topic `operator/pd_gains` | `JointPdGainsFile` | the robot's MRT joint controller |
| `humanoid_nmpc/humanoid_mpc_config/config_registries.textproto` | `ConfigRegistries` | the GUI: the names a registry string may take |

Each file starts with its schema, which the parsers check and `make lint` requires (`textproto-header`):

```textproto
# proto-file: humanoid_nmpc/humanoid_mpc_config/task_file.proto
# proto-message: humanoid_mpc_config.TaskFile
```

Nothing in the stack reads YAML: `make lint` refuses a `.yaml` file under `robot_models/` or `humanoid_nmpc/` and any
use of yaml-cpp (`config-yaml`, `yaml-cpp`, AGENTS.md).

## Schema map

Every `.proto` file holds one message, named after the file. The task file's blocks, by the field that holds them:

| Field of `TaskFile` | Message (file) | What it sets |
|---|---|---|
| `interface` | `InterfaceConfig` | the interface's own flags (`verbose`) |
| `model_settings` | `ModelSettingsConfig` | the robot model: its name, the joints the MPC fixes, the 6-DoF contacts, the arm-swing joints, the CppAD flags, the foot constraint gains |
| `multiple_shooting`, `rollout`, `mpc` | `SqpSettingsConfig`, `RolloutSettingsConfig`, `MpcSettingsConfig` | the SQP solver, the rollouts and the MPC loop (`toSqpSettings()` and the others, defaults of the OCS2 structs) |
| `initial_state` | `StateValues` | the initial state, by name |
| `state_weights`, `final_state_weights` | `StateWeights` | the running and the terminal state weights, by name |
| `input_weights` | `InputWeights` | the input weights: each contact's wrench, then the joint velocities (centroidal) or accelerations (whole body) |
| `com_weights`, `acom_weights` | `ComWeights`, `AcomWeights` | the center-of-mass and angular-center-of-mass tracking of `com_and_acom_tracking_cost` |
| `left_leg_torque_cost`, `right_leg_torque_cost`, `joint_torque_weights` | `JointWeights` | joint torque costs: the legs' (centroidal), every joint's (whole body) |
| `task_space_foot_cost`, `task_space_costs` | `TaskSpaceCostConfig` with `TaskSpaceWeights` | the swing-foot cost and the named link costs; the whole-body foot cost refuses a non-zero `pos_x`, `pos_y` or `pos_z`, weights of a position error it does not have |
| `contacts` | `ContactsConfig` | the contact geometry, the wrench cone, the basis-vector inputs, the friction cone |
| `joint_limits`, `collision_constraint`, `mimic_joints` | `JointLimitsConfig`, `CollisionConstraintConfig`, `MimicJointsConfig` | soft and hard constraints |
| `dcm_terminal_cost`, `icp_cost_weights` | `DcmTerminalCostConfig`, `IcpCostWeights` | the centroidal MPC's capture-point costs |
| `swing_trajectory_config` | `SwingTrajectoryConfig` | the swing-foot trajectories |
| `locomotion_heuristics` | `LocomotionHeuristicsConfig` | the reference-shaping heuristics (humanoid_nmpc/docs/locomotion_heuristics/README.md) |
| `nominal_foothold`, `contact_implicit` | `NominalFootholdConfig`, `ContactImplicitConfig` | the nominal foothold reference; the contact-implicit terms |
| `contact_wrench_gate`, `mpc_link` | `ContactWrenchGateConfig`, `MpcLinkConfig` | the robot process: touch-down shaping of the planned wrenches, the remote MPC link |

The task file's scalars and lists set the formulation (`costs`, `soft_constraints`, `hard_constraints`,
`contact_input_parameterization`, `contact_schedule_source`, `centroidal_model`, `terminal_cost_scaling`,
`terrain_height`), the robot process and the simulator (`contact_estimator`, `telemetry_sinks`, `telemetry_frequency`,
`gantry_hold`, `sim_*`, `wb_mpc_feedforward`, ...), the visualization's frames and rate, and the GUI's
`enable_online_tuning`. The other files:

- `reference_file.proto`: the command limits and filter, the default posture `default_joint_state` (`JointValue`
  entries) and the gait schedule's start (`ModeScheduleConfig`, `ModeSequenceTemplateConfig`).
- `gait_file.proto`: the gaits by name (`ModeSequenceTemplateConfig`).
- `joint_pd_gains_file.proto`: the gains every joint starts from and those of named joints.
- `contact_planning_file.proto`: the planner, its shared and H-LIP blocks, the term lists and a block per term
  (humanoid_nmpc/docs/contact_planner_ocp_refactor/README.md).
- `mpc_parameter_update.proto`: the GUI's live update, a whole `TaskFile` and, for a robot that has one, a whole
  `ContactPlanningFile`.
- `xyz.proto`, `yaw_pitch_roll.proto`, `joint_value.proto`: the shared primitives of the weights and values.
- `tuning_options.proto`, `tuning_group_options.proto`, `config_options.proto`: the GUI metadata ([below](#gui-metadata)).
- `config_registries.proto`: the registries' names ([below](#gui-metadata)).

## Conventions

- **One message per file**, named after it, edition 2023, `option (nproto.generate_struct) =
  "ocs2::humanoid::mpc_config::<Name>";` first, `// Next ID: N` above every message and `reserved N to max;` first
  after the options (tools/hooks/proto_file_layout.py, proto_next_id.py). A block used by one file only is nested in
  it; a block used in several places has its file. `config_options.proto` is the one options-only file.
- **Names** are snake_case (`state_weights`, `abs_tol_ode`, `ssp_duration`); a control of the GUI is labeled by them.
- **Defaults.** A scalar whose absence means "the default" carries `[default = X]`, the default of the domain struct it
  converts to, and is a plain struct member. A scalar whose absence has its own meaning (unset, the controller's
  default, derived from the robot model as a `com_height` left out is, or required by the formulation that reads it)
  has no default and is a `std::optional`, never a sentinel value such as 0; so is a message field
  marked `[(nproto.optional_message) = true]`. Strings carry `[default = ""]` unless absence means something.
- **An absent list is empty.** A repeated field has no presence: a file that leaves out `telemetry_sinks`,
  `sim_visualizations` or a term list has none, so the shipped files write every list out.
- **Weights and states by name**, never by index: `{x y z}` blocks, the base orientation as Euler `{yaw pitch roll}`
  (also where the MPC's orientation is a quaternion), and joints as `joint_positions { joint: "back_bkz" value: 5 }`.
  The conversions place each name at the index the MPC's model gives it (`StateInputLayout`), require every joint of
  the model exactly once and refuse an unknown or a fixed one, naming it.
- **Named components are strings** that a registry resolves (costs, constraints, estimators, sinks, visualizations,
  parameterizations, the centroidal model, the stance constraint's rows, the foot cost's phases, the planner's
  threading, its terms and its terminal DCM target, heuristics), never booleans or int codes. Each such field names its registry in its tuning
  options (`registry: "contact_estimator"`) and is tied to the registry's name list with `LINT.IfChange` /
  `LINT.ThenChange`.

## Reading a file

`nproto::LoadTextprotoFile<mpc_config::TaskFile, humanoid_mpc_config::TaskFile>(path)` parses a file strictly into its
struct; `humanoid_common_mpc/config/ConfigFiles.h` wraps it per file kind (`loadTaskFile()`, `loadReferenceFile()`,
...), with the file named in every error. A file whose header names another message is refused before it is parsed. A
retired key is refused with what replaced it ([below](#retiring-a-hyperparameter)). Python reads the same files with
`nproto_textproto.load_textproto(path, task_file_pb2.TaskFile)`, which refuses what the C++ parser refuses, at the
same position.

The structs are the API. The conversions, `humanoid_<pkg>/include/.../config/<area>/*FromConfig.h`
(`stateWeightsFromConfig()`, `toSqpSettings()`, `swingTrajectorySettingsFromConfig()`, ...), take a block's struct and
return the domain struct or an `InvalidArgument` naming the field path. Only the entry points of a process take a path: the MPC interfaces'
`Create`, `ModelSettings::Create`, the target trajectories calculators' `Create`, `ProceduralMpcMotionManager::Create`,
`GaitSchedule::Create`, the MRT joint controllers' `Create`, the parameter updater, `loadRobotProcessSettings`,
`loadVisualizationConfig`, `loadKeyboardCommandLimits` and the task-file watcher. Each loads the file and calls its
typed overload. `bazel run //tools/config_dump -- --robot=<robot>` prints everything they build from a robot's files.

## Live updates

The tuning GUI publishes typed messages, never text: the whole edited task file (and contact planner's file) as an
`MpcParameterUpdate` on `operator/mpc_parameters`, and the whole PD gains file as a `JointPdGainsFile` on
`operator/pd_gains`. The file watches of the running stack parse the edited file the same way.

**A reload is the file.** A running stack applies an update, or an edited file, as that whole file: a block it leaves
out is the block's defaults, exactly as at start-up, not the value it ran with. The fields applied while running are
the ones the schema marks `RELOAD_HOT`. A block that does not convert is logged by its field path and keeps its running
values; the rest of the file still applies.

**Both formulations tune live.** The MPC node of each formulation registers one `MpcParameterUpdaterModule`
(`humanoid_common_mpc/parameter_update/`), a synchronized module of the SQP solver that runs on the MPC's machine
before each solve, never on the robot's realtime thread. It takes the latest update from the bus and the edits of the
task file and the reference file it watches, and hands the reloaded task file to the formulation's appliers, each of
which writes its fields into every worker's copy of the running problem: the centroidal MPC's
(`centroidalHotFieldAppliers()`, `humanoid_centroidal_mpc/mrt/CentroidalMpcParameterUpdater.h`) and the whole-body
MPC's (`wholeBodyHotFieldAppliers()`, `humanoid_wb_mpc/parameter_update/WholeBodyHotFieldAppliers.h`). A weight the CppAD code generation tapes enters
the generated code as a parameter, so an update is a parameter write: nothing is taped or compiled again. The updater
logs, by field path, every `RELOAD_START_UP` field that this MPC reads (no `consumer`, or `"mpc"`, and its own
formulation's) and that differs from the file the MPC started with, as taking effect at the MPC's next start; the
robot process's `RELOAD_START_UP` fields are logged apart, as read at the robot's next start from its own copy, and the
GUI's fields and the other formulation's are not reported. An entry added to, removed from or renamed in
`task_space_costs`, or a changed `link_name`, is such a field: a reload applies the weights of the link costs the
running problem carries and names the others. A field the schema marks for one formulation only (`formulations`,
[GUI metadata](#gui-metadata)) is not applied by the other one, which never read it.

**One solve late.** `terrain_height` and `swing_trajectory_config` reach the reference manager, whose references of a
solve are built before the updater runs (`SolverBase::preRun`). An update of either takes effect at the solve after the
one it arrived before; the first run on a new ground then lifts the target in use by the change, once.

The robot process applies the fields marked `consumer: "robot"` (`contact_estimator`, `contact_wrench_gate`) from the
same update and from its own copy of the task file.

## Version skew

A GUI and a robot or an MPC node built from different versions of these schemas cannot exchange the payloads: a
receiver refuses, logs and counts every `MpcParameterUpdate`, `JointPdGainsFile` and `DodgeballThrow` that carries a
field its schema does not know (`nproto::UnknownFieldPaths()`), and every `MpcParameterUpdate` whose
`schema_fingerprint` is not its own (`nproto::SchemaFingerprint()`, which the GUI stamps with
`nproto_schema.schema_fingerprint()`): nothing of it is applied
(`humanoid_common_mpc/config/OperatorPayloadChecks.h`). A payload under the same type name used to be applied in
part, the fields one side lacked silently dropped or defaulted. An `MpcParameterUpdate` whose task file names another
robot (`model_settings.robot_name`) is refused the same way, and so is one whose `config_path` - the task file's path
from `robot_models/` on - is not the configuration the receiver runs: the centroidal and the whole-body G1 share the
robot name `g1`, and the path keeps a GUI opened on one from retuning the other. The GUI's Save sends the robot its copy
of the files it reads as a `humanoid_mpc_msgs.ConfigFileSave` (`operator/config_save`), carrying the file's kind, robot
name, `config_path`, the schema fingerprint of the file's message and the exact saved text; the robot refuses one of
another robot, configuration or schema, or one its strict parser refuses, and keeps its copy. Rebuild both sides from
one commit.

## Adding a hyperparameter

1. Add the field to its block's message, with the next free number (update `// Next ID` and `reserved N to max;`),
   its unit in a comment and in `unit`, and `[default = X]` equal to the domain struct's default (or no default where
   absence has its own meaning, [Conventions](#conventions)).
2. Give it its tuning options where the block's do not fit: `reload` (`RELOAD_HOT` only where the running stack applies
   it), a slider range or `log_scale`, `registry` for a name, `formulations` for a field one MPC formulation reads,
   `active_when` for one that applies only under a setting of another field, or `exclude_reason` for one that gets no
   control.
3. Read it in the block's conversion (`*FromConfig.cpp`) into the domain struct, and, for a `RELOAD_HOT` field, in what
   the running stack reapplies: the applier of each formulation that reads it (`staticFields()` of a `HotFieldApplier`
   in `centroidalHotFieldAppliers()` or `wholeBodyHotFieldAppliers()`), or the robot's controller-side settings.
4. Write it in the shipped files where a robot needs a value other than the default.

Nothing else: the GUI renders it from the descriptor, the editor saves it, and the bus carries it. The tests catch what
was left out ([Tests](#tests)): a field no conversion reads (T4), a field without its reload class or with a hot class
that the updater of a formulation reading it does not apply (T8), and, in the block's own conversion test, a default
that differs from the struct's (T3).

## Retiring a hyperparameter

Delete the field, keep its number out with `reserved N;` (never `reserved "name";`, which the C++ text parser silently
skips: `make lint` refuses it), and name the old key in its message's options:

```proto
option (nproto.retired_field) = { name: "use_dcm_terminal_cost" replacement: "list dcm_terminal_cost under costs" };
```

A file that still sets it is refused, in C++ and in Python, with `task.textproto:12:1: 'use_dcm_terminal_cost' is
retired: list dcm_terminal_cost under costs`; the name matches its camelCase and snake_case spellings. A retired name
must not be a live field of the message (the generator refuses it). A key whose block moved can be answered for the
whole message with `option (nproto.retired_layout_hint) = "..."` (tools/nproto/README.md, "Retired fields").

## GUI metadata

<!-- LINT.IfChange(config_options) -->
`config_options.proto` declares the field option `(humanoid_mpc_config.tuning)`, a `TuningOptions`
(`tuning_options.proto`: slider range, log scale, unit, exclusion reason, reload class, registry, applicability
condition, consumer, formulations), and the message option `(humanoid_mpc_config.group)`, a `TuningGroupOptions` (the tab of a block
and its order on it). The tuning GUI renders every numeric, bool and registry-string field from the descriptors with
them, so a new hyperparameter needs a schema field and its conversion, and no GUI code.
<!-- LINT.ThenChange(//humanoid_nmpc/humanoid_mpc_config/config_options.proto:config_options) -->

- **Inheritance.** A block's options apply to every field below it unless the field sets its own; `registry` is each
  field's own, and the `active_when` conditions of the blocks above a field add up. A shared message (`Xyz`,
  `JointValue`) is annotated where it is used.
- **Labels are field names.** A control is labeled by the dotted path of its field names, each list element by its key
  (`joint_positions[back_bkz]`), with its unit and what the options add ("restart", "not applicable: ..."). There is
  no label option, and the comments of a file are never part of a label.
- **Registries.** A registry string is a drop-down of the names its registry accepts, which
  `config_registries.textproto` lists. `bazel run //tools/config_registries:print_config_registries` writes it from
  the linked registries, and `//tools/config_registries:config_registries_test` fails when it and the registries
  differ (tools/config_registries/README.md).
- **Consumers.** `consumer` says who reads a field when it is not the MPC (`robot`, `gui`); the consumption test (T4)
  exempts a field the C++ stack does not read only with what reads it.
- **Formulations.** `formulations` names the MPC formulations that read a field (`"centroidal"`, `"whole_body"`; empty:
  every one), inherited like `reload`: `com_weights`, the capture-point costs, the link and leg torque costs,
  `contact_implicit`, `locomotion_heuristics`, the basis-vector blocks of `contacts` and `stance_constraint` are the
  centroidal MPC's; `joint_torque_weights` and the acceleration gains of `foot_constraint` the whole-body MPC's. The GUI
  labels a field the file's formulation does not read "not applicable", and T8 expects a hot field in the applied
  fields of exactly the formulations that read it.

The GUI's side is humanoid_nmpc/remote_control/README.md, "Tuning the configuration".

| Target | What |
